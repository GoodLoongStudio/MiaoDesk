## AI 对话里的 `/provider` 不再把 Key 发到别的服务 — 2026-10-04

- **任务**：P0-07（App 重启状态一致性，AI 侧）。
- **用户可感知变化**：在 AI 对话里敲 `/provider https://别的服务/v1 某个模型` 之后，
  之前**下一次请求会把你在"API 配置"里那个配置的 Key，发到你刚敲的这台新服务上去** ——
  一把签给 A 服务的 Key 被送到了 B 服务。更糟的是 `/key`：它会把你在对话里敲的新 Key
  **覆盖掉"API 配置"里那个配置自己存的 Key**，而设置界面里一个字都不提，之后每一个用
  该配置的 AI 窗口都用上这把被换掉的 Key。
  现在换主机时凭据跟着换来源（不再复用原配置的 Key，`/key` 写的位置也变成同一个），
  你填的地址一个字符都不变。只改端点路径（`/endpoint`，主机没变）时不受影响。
  另外 `/provider` 的回复原先固定说"模型配置已保存。"，而那其实**不会跨重启保留**
  （API 配置中心才是权威来源）；现在如实说明。
- **验证级别**：本机自动检查（新增 38 项纯逻辑判定 + 反空洞自检 + 16 处变异全红 +
  21 道仓库门 + mingw 交叉语法门）通过；**Windows 真机未验证** —— 改动都在
  `L3Agent`（Win32 凭据/HTTP）里，桌面上的实际请求未签收。

## 校验器不再拒绝随产品发行的内容包 — 2026-10-03

- **任务**：D-6/CAP-03（回归门首次跑出）。
- **用户可感知变化**：内容包的**包级校验**此前要求 `manifest.json` 的 `entry` 以
  `scene/` 开头，而三个内置壁纸、三个内置组件和两个示例包用的都是根下的 `scene.json`。
  照这些合法包的样式写出来的内容，会被判"校验不通过"，提示是"entry 必须指向 scene/ 下的
  一个 .json 文件"——而那句话指向的正是能正常加载的包。现在两种布局都接受；仍然拒绝
  `assets/a.json`、`manifest.json`、`scene/scene.png` 和越出包根的路径。
  这一条此前没有任何自动检查覆盖，因为既有的 `BuiltinWallpaperPackages` 走的是另一条链
  （load → 场景校验 → 初始化），不跑包级校验。
- **验证级别**：本机自动检查（新增发行包包级校验门 + 131 项校验器断言 + 变异检测）通过；
  **Windows 真机未验证**。

## 两条动画写同一个属性现在被拒绝 — 2026-10-03

- **任务**：WALL-03（动画、状态与有界行为）。
- **用户可感知变化**：内容场景里两条动画写同一个属性此前**不报错，也看不到其中一条**：
  先声明的那条从来不出现在桌面上（它连起始值都贡献不了，另一条每帧都把它盖掉）；
  事件触发的那条更糟 —— 它只在触发那一帧赢一帧，之后又被时间线动画盖回去，
  看起来是一次一帧的闪。现在这类内容**加载失败**，错误信息直接点名是哪两条
  （"`animation://a` 与 `animation://b` 都写 `component://…/opacity`"），
  而不是只告诉你是哪个属性。随产品发行的 8 个包逐个确认不触发这一条。
- **没变的一条**：一条绑定（binding）和一条动画写同一个属性**仍然合法**，而且是一个
  自洽的写法 —— 绑定只在场景初始化时跑一次，它给的是起始值，动画一开跑就接管。
  这里要小心的只有一件事：别指望绑定在动画跑起来之后还能压住它，引擎里没有叠加。
- **未变**：`SceneClock`（暂停/恢复不跳变）与参数平滑过渡这两个新能力本轮**还没有接到
  任何界面**，桌面上暂时看不到差别 —— 它们属于播放宿主那一轮，因为要先决定暂停由谁调、
  参数面板失焦后怎么办。循环接缝与一帧瞬移的审查也已就位，但那是对**将来**的保护：
  三个内置壁纸当前没有循环接缝问题。
- **一个已知未修**：`MiaoCloud` 的"眨眼"淡入/淡出各为 1/240 秒，也就是产品支持的最高
  帧率下的一帧，所以那一"淡变"在任何帧率下都渲染不出来，实际看到的是硬切。
  没有改它：改法是拉长淡变，那是改美术，而本机不是 Windows，拉长之后好看不好看
  给不出证据。代码里以登记表的形式盯着这件事。
- **验证级别**：本机自动检查（174 项时间策略断言 + 48 项发行内容审查 + 6 项新的拒绝断言，
  26 处变异全部变红）通过；**Windows 真机未验证**。

## 组件宽高比字段不生效(已如实写明) — 2026-10-04

- **任务**：WPRO-01（组件尺寸族与自适应布局）的度量一半。
- **用户可感知变化**：写内容包的作者此前被告知 `geometry.aspectRatio` 声明宽高比。
  实际情况是：这个字段**没有任何渲染器或宿主编译出来**。校验只比较
  `defaultWidth / defaultHeight`（归一化之比），于是 0.30/0.30 = 1.0 会通过；而组件真正
  拿到的像素盒是"归一化宽 × 屏幕宽"与"归一化高 × 屏幕高"。在 16:9 屏幕上，声明 `1.0`
  的组件实际拿到 576×324 像素(1.78:1),在 32:9 上是 1.78 倍与 3.56 倍的失真。
  三个随内置的组件全都声明了 `1.0`,八块常见屏幕上一个也不成立。
  现在文档与 Skill 说实话：写它不会报错，也不会生效；组件真实拿到的比例是
  `(归一化宽 / 归一化高) × (屏幕宽 / 屏幕高)`,想要接近目标比例的方块请按这个式子
  反推 `defaultWidth / defaultHeight`。
- **没变**：三个内置组件在桌面上的外观**一个都没动** —— 那需要 Windows 才能验证效果,
  而"为了过一道门去改一个看不见效果的东西"正是这个项目禁止的动作。所以本轮只把
  "现在实际是多少"算出来、写清楚、并设一道门登记它。
- **验证级别**：本机自动检查（61 项几何断言 + 10 项发行内容审查 + 14 条 JSON 读取器
  新断言，13 处变异全部变红）通过；**Windows 真机未验证**。

## 画不出来的组件不再每 16 毫秒重试一次 — 2026-10-04

- **任务**：WPRO-05（组件更新调度与能耗）。
- **用户可感知变化**：一个内容坏了/画不出来的桌面组件，此前每一帧都在重试 ——
  一秒 60 次、一天 520 万次，每次都重跑渲染目标、渲染器和宿主数据整条链路。
  原因是"下一次何时重画"只在一次**成功**绘制时被设置；五条失败路径都不设置它，
  而未设置的值在宿主那里的含义是"随时都该画"。现在失败会指数退避
  （1秒、2秒、4秒、8秒、16秒，30 秒封顶），一分钟最多 2 次而不是 3750 次；
  一旦画成功一次，立刻回到内容本来要的刷新间隔。
- **没变**：正常工作的组件的刷新节奏一个都没动（空闲 1 秒、要帧时按帧调度器）。
  实际省下多少 CPU 与电**没有测量** —— 那需要 Windows 实机，本机给不出来。
  本轮只修缺陷方向，不声称省了百分之几。
- **验证级别**：本机自动检查（174 项刷新调度断言，7 处变异全部变红）+ mingw 交叉
  语法门（0 真实错误）通过；**Windows 实机测量未做**。

## 组件诊断行现在报告真实宽高比 — 2026-10-04

- **任务**：WPRO-01（组件尺寸族与自适应布局）的接线一半。
- **用户/支持者可感知变化**：桌面组件的诊断行（配置文件 Diagnostics 段与运行日志）现在多出
  四个字段：`aspectDeclared` / `aspectActual` / `aspectDistortion` / `aspectHonored`。
  三个内置组件在 1920×1080 上会打印 `aspectDeclared=1.000 aspectActual=1.778
  aspectDistortion=1.778 aspectHonored=false` —— 也就是"manifest 声明正方形、实际拿到
  1.78:1"这件事现在写得出来，此前只能由人对着屏幕量和对着 manifest 猜。
  没声明 `aspectRatio` 的组件不写这一段。
- **没变**：壁纸与组件的**视觉表现一个像素都没动**。`aspectRatio` 仍然没有任何渲染器读它，
  所以声明 1.0 的组件在桌面上还是 1.78:1。本轮只是让这件事不再安静 —— 修它要动渲染，
  而"为了过一道门去改一个看不见效果的东西"正是这个项目禁止的动作。
- **验证级别**：本机自动检查（75 项几何断言 + 4 处变异全红 + mingw 交叉语法门 0 真实错误）
  通过；**诊断行的实际输出未在 Windows 上看过**，桌面视觉未签收。

## 桌面组件的坏几何不再自我延续 — 2026-10-04

- **任务**：P0-04（Widget 20 次创建/启停/删除循环）的自动部分。
- **用户可感知变化**：桌面组件的归一化几何此前**不挡 NaN**。`std::clamp` 对 NaN 是恒等函数，
  而配置读取用 `wcstof` 且不查有限性、写回又用 `%.6f` —— 一个 NaN 会写进配置文件、
  再读回来、再写回去，一直坏下去。带着 NaN 坐标的组件在 `UpdateLayeredWindow` 上直接失败
  或从桌面上消失，而用户看到的只是"那个组件莫名不见了，重启也一样"。
  现在读配置与归一化两侧都把非有限值换成默认值。
  另外"同一原生预设在同一台显示器上只允许一个实例"这条规则，与"位置/尺寸夹紧后不越界"
  这组不变量，现在每轮都在本机真跑 —— 此前它们住在一个为了配置持久化而 import 了
  Windows 头的 .cpp 里，一行都验不到。
- **没变**：组件在桌面上的外观**一个像素都没动**（合法输入的归一化结果与原来逐位相同）。
  P0-04 的"无孤立 HWND、错误背景"与 20 次循环本身仍未做，那要 Windows 真机。
- **验证级别**：本机自动检查（126 项几何与去重断言，11 处变异全部变红）通过；
  **Windows 真机未验证** —— 修的是坏值的链条，不是它在桌面上的现象。

### Added · AI

- **妙喵 AI、壁纸 Creator、组件 Creator 支持持久多会话。**
  默认继续上次对话；用户可创建新对话并从历史切回旧会话；退出程序或 Windows 重启后仍可恢复。

- **Creator 历史与作品 workspace 绑定。**
  切回旧创作对话时，同时切回对应内容工作区，避免“聊天是旧作品、实际改到新作品”。

### Improved · Development

- **ARM64 快速开发链改为云端编译 + 小型 Overlay。**
  测试机不需要 CMake/Visual Studio，双击 `ARM64-Quick-Test.cmd` 即可同步、下载、验证并启动 Dev 版本。

- **ARM64 编译接入跨 Runner sccache。**
  热缓存曾实测达到 124/124 cache hit，显著缩短日常 ARM64 编译等待。
